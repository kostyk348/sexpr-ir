# sexpr-ir

Эксперимент: **исполняемый S-expression IR** для проверки переimplementаций
функций macOS-фреймворков до того, как они зафиксированы в C/Obj-C.

Прототип написан на Common Lisp (SBCL) и не требует зависимостей.

## Зачем

Цикл при разработке стаба Darling/VibeDarling сейчас такой:

```
написать C/Obj-C → скомпилировать → слинковать → запустить тест →
сравнить → отредактировать → повторить
```

Компиляция и линковка доминируют во времени итерации, особенно когда
агент генерирует десятки кандидатов-реализаций.

Идея: сначала описать **логику** решения в S-expression, прогнать её на
корпусе моков за микросекунды, поправить узлы AST — и только потом
печатать C. Финальный артефакт остаётся C/Obj-C; IR — слой проверки рядом
с существующей сборкой, а не замена ей.

## Почему S-expression, а не JSON или свой DSL

AST читает **родной ридер Lisp**: `read-from-string` возвращает форму,
которая одновременно является данными. Своего парсера в проекте нет —
это и есть выигрыш гомоиконичности.

```lisp
(read-from-string "(:function f (:params (x)) (:body (:+ x 1)))")
;; => (:FUNCTION F (:PARAMS (X)) (:BODY (:+ X 1)))
```

## Что умеет прототип

- чтение IR формы ридером Lisp;
- интерпретация: `:if`, `:null`, `:not`, `:eq`, `:>=`, `:<=`, `:>`, `:<`,
  `:and`, `:or`, `:+`, `:-`, `:*`, `:field`, `:mem/read`, `:syscall`;
- моки объектов и системных вызовов;
- корпус тестовых случаев на функцию с отчётом ok/fail;
- генератор C из IR;
- замер скорости;
- REPL: `(sexpr-repl)`.

## Запуск

```bash
SBCL_HOME=/usr/local/sbcl/lib sbcl --script run.lisp
```

Прогон печатает корпус по каждой функции, сгенерированный C и замер
скорости. Код выхода 0 — все случаи прошли, 1 — есть провалы.

REPL:

```bash
SBCL_HOME=/usr/local/sbcl/lib sbcl --load ir.lisp --eval '(sexpr-repl)'
```

Внутри REPL: форма `(:function ...)` регистрирует функцию, `(c <форма>)`
печатает C, `(run <имя>)` гоняет корпус, `(demo)` — демо, `exit` — выход.

## Реальные функции VibeDarling

Модели взяты из настоящего кода, а не придуманы.

Источник: `github.com/VibeDarling/darling-foundation`,
коммит `36f348ca7392a26034ab6332db7d2ed32da5182c`.

### 1. `-[NSConstantArray objectAtIndex:]`

`src/ModernStubs.m:16-25`:

```objc
- (id)objectAtIndex:(NSUInteger)index
{
    if (index >= _count)
    {
        [NSException raise:NSRangeException format:@"Index %lu out of bounds [0, %lu)", (unsigned long)index, (unsigned long)_count];
        return nil;
    }
    return (id)_objects[index];
}
```

IR (`-1` вместо исключения, индекс вместо объекта — проверяется именно
граничное условие `>=`):

```lisp
(:function objc_constant_array_object_at_index
  (:params (index count))
  (:body (:if (:>= index count) -1 index)))
```

Случаи: `(0 3)=0`, `(2 3)=2`, `(3 3)=-1`, `(4 3)=-1`, `(0 0)=-1`.

### 2. `-[NSByteCountFormatter stringFromByteCount:]` — выбор основания

`src/NSByteCountFormatter.m:125-134`:

```objc
unsigned long long thousand = 0;
switch (_countStyle)
{
    case NSByteCountFormatterCountStyleBinary:
    case NSByteCountFormatterCountStyleMemory:
        thousand = 1024;
        break;
    default:
        thousand = 1000;
        break;
}
```

IR:

```lisp
(:function objc_bytecount_thousand
  (:params (style))
  (:body (:if (:or (:eq style 0) (:eq style 1)) 1024 1000)))
```

Случаи: `0→1024`, `1→1024`, `2→1000`, `3→1000`.

### 3. `-[NSByteCountFormatter stringFromByteCount:]` — adaptive fraction digits

`src/NSByteCountFormatter.m:182-195`:

```objc
NSUInteger fractionDigits = 2;
if (_adaptive)
{
    if (unitIdx <= 1)
    {
        fractionDigits = 0;
    }
    else if (unitIdx == 2)
    {
        fractionDigits = 1;
    }
}
```

IR — и здесь первая настоящая находка:

```lisp
(:function objc_bytecount_fraction_digits
  (:params (unit-idx adaptive))
  (:body
    (:if (:not (:eq adaptive 0))
         (:if (:<= unit-idx 1) 0
              (:if (:eq unit-idx 2) 1 2))
         2)))
```

## Находки

### Находка 1: правдивость нуля в C и в Lisp противоположна

Первая версия IR повторяла C буквально:

```lisp
(:if adaptive ...)   ; adaptive = 0
```

В C `0` — ложь, в Lisp `0` — **истина**. Случай `(unit-idx 0, adaptive 0)`
дал `0` вместо ожидаемых `2`, и корпус это поймал за микросекунды, до
всякой компиляции.

Починка — сделать условие явным (`(:not (:eq adaptive 0))`), что заодно
документирует разницу семантик прямо в IR.

Это ровно тот класс ошибок, ради которого затевался эксперимент: он
вылез бы только после `compile → link → run`, и то если бы в тесте был
случай с `adaptive = 0`.

### Находка 2: корпус важнее компилятора

Ни один из провалов не был синтаксическим. Оба раза ломалось
**поведение** на границах (нулевая длина массива, нулевой флаг), а
компилятор такие вещи не ловит вообще.

## Замер

| Что | Время |
| --- | --- |
| IR: один прогон функции | **0,06 мкс** |
| IR: полный корпус (15 случаев) | единицы микросекунд |
| IR: весь скрипт со стартом SBCL и бенчем на 100 000 прогонов | 55 мс |
| Нативный цикл: `gcc -O2` компиляция + линковка | 143 мс |
| Нативный цикл: прогон тех же 15 случаев | 1 мс |
| **Нативный цикл целиком** | **144 мс** |

То есть проверка кандидата падает со ~144 мс до микросекунд — на четыре
порядка, при том что финальный артефакт остаётся C/Obj-C.

Критерий успеха из постановки — «провалидировать кандидата меньше чем за
1 секунду» — выполнен с запасом в шесть порядков.

## Границы и не-цели

- Это **не** замена Mach-O-загрузчика, darlingserver или
  переimplementаций фреймворков.
- Это **не** утверждение, что S-expression — финальный артефакт.
  Финальный артефакт остаётся C/Obj-C.
- Это **не** переписывание Darling на Lisp.
- Моделируется только решающая логика. Объектная обвязка (`NSException`,
  `NSString`, аллокации) остаётся в ObjC и здесь заменена моком; границы
  такой замены надо держать в голове.
- Генератор C покрывает подмножество IR; неподдержанные формы печатаются
  как `/* не поддержано */ 0`, а не угадываются.

## Что дальше

- Добавить `:let` и сравнение структур, чтобы моделировать функции,
  которые возвращают не число.
- Сравнивать IR-модель с поведением оригинального бинаря macOS на одном
  и том же корпусе — это следующий шаг после прототипа.
